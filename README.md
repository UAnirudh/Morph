# Morph

**Describe how you want your workspace to work. Morph rewrites the interface to match.**

Morph is a working CRM whose UI is generated from a validated JSON schema. You type
what you need in natural language — *"prioritize revenue, pipeline health, and overdue
follow-ups"* — and Morph produces a schema transformation, shows you a preview against
your real data, and applies it as a new, undoable version. The CRM data underneath never
changes; only the way it is presented and automated does.

This is an MVP built to be demonstrated end to end, not a mock. Every metric, table,
chart, board and quick action on the canvas reads live workspace data through the same
data access layer, and every transformation is validated before it can touch the
interface.

## Quick start

Requirements: **Node.js 20+** (developed on Node 24) and npm.

```bash
git clone <your-fork-url> morph && cd morph
npm install

# Optional — the app runs with zero configuration:
cp .env.example .env.local

npm run db:migrate   # create ./data/morph.db and apply migrations
npm run db:seed      # deterministic demo workspace, 26 leads, 12 deals, ...
npm run dev          # http://localhost:3000
```

Open <http://localhost:3000> and either create an account (you land in a freshly
seeded workspace of your own) or use the demo account:

```
demo@morph.app / morph-demo
```

The demo password comes from `MORPH_DEMO_PASSWORD` (default `morph-demo`). Creating a
new account is enabled by `MORPH_ALLOW_SIGNUP=true`; each new account gets its own
isolated workspace, so two browsers never see each other's records.

### With a model provider

Groq and OpenAI speak the same chat-completions protocol, so Morph drives both through
one client. Start on Groq's free tier, add an OpenAI key later — no code change:

```bash
# .env.local — starting out on Groq
GROQ_API_KEY=gsk_...

# later, once funded (OpenAI wins when both are present)
OPENAI_API_KEY=sk-...

# optional overrides
MORPH_AI_PROVIDER=groq            # force one provider while both keys exist
MORPH_AI_MODEL=openai/gpt-oss-120b # Groq default; OpenAI default is gpt-4o-mini
# MORPH_AI_BASE_URL=https://api.groq.com/openai/v1  # any compatible endpoint
```

Resolution order: `MORPH_AI_PROVIDER` → `OPENAI_API_KEY` → `GROQ_API_KEY` → local planner.

Restart the dev server. The AI panel header switches from **Local planner** to
`Groq · openai/gpt-oss-120b` (or the OpenAI model), and new proposals are generated by
the model. If the provider is unreachable or returns invalid output, Morph falls back to
the deterministic planner, labels the result honestly, and tells you what happened — it
never pretends a failed call succeeded.

## The five-minute tour

1. **`/` → `/signup`** — create an account. The onboarding wizard asks your role, what
   you want to improve, and which workflows you care about. It provisions a workspace
   seeded with realistic CRM data and builds your first interface from a role preset.
2. **`/studio`** — your generated interface. Every widget is a schema component bound to a
   dataset; every action button performs a real, permission-checked write.
3. **Ask Morph** (right-hand panel, or the drawer on narrow screens) — try
   *"Show team workload, unfinished tasks, and bottlenecks."* A proposal appears with a
   diff summary, assumptions, preserved sections and the engine that produced it. The
   canvas previews it **without** writing anything.
4. **Apply change** — the interface is saved as a new version and the canvas re-renders.
   **Undo** reverts to the previous version (which is itself a new version, so nothing is
   lost).
5. **`/studio/compare`** — the before/after demonstration: pick a persona, generate the
   interface live, and reset the demo when you're done.
6. **`/studio/workflows`** — build an automation, enable it, run it, and inspect the run
   log. The action really happened: tasks were created, records flagged, notifications
   raised.

A timed pitch script lives in [docs/DEMO-SCRIPT.md](docs/DEMO-SCRIPT.md).

## Testing

```bash
npm test          # 73 tests: schema, planner, patch/validation, engine, CRM, workflows, rendering, provider + database target selection
npm run test:e2e  # 10 browser tests: auth, isolation, CRM persistence, transform/undo, workflows, demo, mobile layout
```

- The unit suite runs against an in-memory libSQL database seeded by the same code the
  app uses, with deterministic model-response fixtures — no network access. Current
  output: **9 files passed, 73 tests passed, 1 skipped** (the live-provider smoke test).
- The Playwright suite starts a real dev server against `data/e2e.db` and drives the app
  in Chromium (desktop) and Chromium mobile emulation (Pixel 7 viewport). Current output:
  **9 desktop + 1 mobile tests passed**.
- The live-provider smoke test (`tests/provider.smoke.test.ts`) runs only when
  `OPENAI_API_KEY` or `GROQ_API_KEY` is set, makes one real model call and re-validates
  the response against the transformation schema. Without a key it is skipped, not faked:

  ```bash
  GROQ_API_KEY=gsk_... npx vitest run tests/provider.smoke.test.ts
  OPENAI_API_KEY=sk-... npx vitest run tests/provider.smoke.test.ts
  ```

Headless Chromium needs system libraries. On a normal machine:

```bash
npx playwright install --with-deps chromium
```

On a locked-down container without root, use the bundled fallback:

```bash
./scripts/install-browser-deps.sh   # unpacks .debs under ~/.local/lib/morph-browser
source scripts/browser-env.sh       # LD_LIBRARY_PATH + fontconfig
npx playwright test
```

## Deploying to Vercel

Vercel gives each request a fresh, read-only filesystem, so the local database file
cannot be used there. Morph therefore talks to SQLite through **libSQL**: the same SQL
runs against a local `file:` database in development and against
[Turso](https://turso.tech) in production.

1. **Create the database** (free tier, no card):

   ```bash
   curl -sSfL https://get.tur.so/install.sh | bash   # or: brew install tursodatabase/tap/turso
   turso auth signup
   turso db create morph
   turso db show morph --url        # -> libsql://morph-<org>.turso.io
   turso db tokens create morph     # -> the auth token
   ```

   Optionally create the schema and demo data now, against the hosted database, instead
   of waiting for the first request:

   ```bash
   TURSO_DATABASE_URL=libsql://… TURSO_AUTH_TOKEN=… npm run db:migrate
   TURSO_DATABASE_URL=libsql://… TURSO_AUTH_TOKEN=… npm run db:seed
   ```

2. **Import the repo** at <https://vercel.com/new>. Next.js is detected; no build
   settings need changing. `vercel.json` already adds a daily cron for the workflow
   engine.

3. **Add environment variables** (Project → Settings → Environment Variables), for both
   Production and Preview:

   | Name | Value |
   | --- | --- |
   | `TURSO_DATABASE_URL` | the `libsql://…` URL |
   | `TURSO_AUTH_TOKEN` | the token |
   | `GROQ_API_KEY` | your Groq key — free tier, start here |
   | `MORPH_CRON_SECRET` | any long random string, for the cron route |

   Nothing else is required. Session cookies are random 256-bit tokens stored hashed in
   the database, so there is no signing secret to manage.

4. **Deploy.** The first request applies migrations and, if the database is empty, seeds
   the demo workspace, so the site is usable immediately. Check `/api/health`:
   `"database":"libsql-remote"` means Turso is wired up, `"provider":"groq"` means the
   model key was picked up. Then sign in as `demo@morph.app` / `morph-demo` (override with
   `MORPH_DEMO_PASSWORD`).

5. **Later, when the OpenAI credit arrives:** add `OPENAI_API_KEY` in the same dashboard
   (optionally `MORPH_AI_MODEL=gpt-4o-mini`) and redeploy. OpenAI then takes priority over
   Groq with no code change; set `MORPH_AI_PROVIDER=groq` to keep Groq while both keys
   exist. Environment variable edits only affect deployments created after them, so a
   redeploy is part of the switch.

Full walkthrough, including self-hosting and what to do when you outgrow one database:
[docs/DEPLOYMENT.md](docs/DEPLOYMENT.md).

## Known limitations

These are deliberate MVP boundaries, documented rather than hidden:

- **One SQLite database.** Local development uses a file; production uses Turso. That
  scales reads and regional replicas well, but there is still a single writer, and Turso's
  HTTP round trips make very chatty write loops slower than an in-process driver. The
  Postgres path is documented, not implemented.
- **No streaming tokens.** Transformations run as a server action; the panel shows
  staged progress ("Parsing intent → Planning → Validating → Rendering preview") but the
  model response is not token-streamed.
- **Rate limiting is in-process.** It protects the single-node deployment; multi-instance
  deployments need a shared store (documented).
- **Local planner coverage is finite.** It understands revenue, pipeline, follow-ups,
  tasks, workload, conversion, leads, deals, activity, automation, simplification and
  accessibility intents. Anything else gets an honest refusal, not a guess.
- **Workflow triggers are the three CRM events plus a daily check.** No arbitrary
  webhooks, no outbound email — the notification channel is in-app by design.
- **Themes and dark mode.** There is one carefully tuned dark theme; light mode is not
  implemented.
- **No file attachments, no email sync, no mobile app.**
- **WebKit/Safari is not in the browser suite** (the CI image has no WebKit libraries);
  the mobile layout test runs on Chromium emulation.

## What I would build next

1. Batch the hot write paths into libSQL transactions (fewer HTTP round trips), or move
   to Postgres with row-level security if the app ever needs a different write model.
2. Token streaming plus a diff view for every operation, so users can see exactly what
   the model proposed before applying.
3. A workflow builder UI that edits conditions graphically instead of via the planner.
4. Real email/Slack notification channels behind the existing `notify` action.
5. A component marketplace: third-party components registered into the same schema
   validator, which is the natural next step for "adaptive software".
